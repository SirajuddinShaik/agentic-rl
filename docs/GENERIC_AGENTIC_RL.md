# Generic Agentic RL — Algorithm and Pipeline README

This document explains the agentic reinforcement-learning system as an algorithm
and data pipeline. It deliberately avoids implementation names. The same design
works for search agents, coding agents, browser agents, workflow agents, or any
environment that can execute a policy, call tools, and return a complete
trajectory.

## TL;DR

The system trains a multi-turn, tool-using policy with **Group Relative Policy
Optimization (GRPO)**.

For every training prompt, it generates a group of independent rollouts in a
harness. Each rollout can contain many model turns, tool calls, tool results,
reasoning, and citations. The harness returns a token-faithful trajectory. A
reward pipeline scores the final behavior and the useful intermediate work.
Within each prompt group, GRPO compares the rollouts to each other and converts
the reward differences into advantages. The trainer updates only the tokens that
were actually generated by the policy, while masking tool results and other
environment observations.

In one equation:

```text
policy update ← advantage of a rollout relative to its peer rollouts
```

The important idea is not merely "reward a correct final answer." The system
also preserves the evidence needed to assign credit for multi-turn behavior:
which rollout found useful evidence, which one wasted calls, which one produced
a supported answer, and which tokens actually caused the outcome.

## 1. Core objects

| Object | Meaning | Typical cardinality |
| --- | --- | --- |
| Prompt / task | One user question or environment task | One per group |
| Group | All rollouts generated for the same prompt | Usually 4–16 |
| Rollout / session | One complete attempt to solve the task | One per sample |
| Turn | One model action and the following environment observation | Many per session |
| Action | A policy-generated span: text, reasoning, structured tool call, or final answer | One or more per turn |
| Tool result | Environment-generated observation returned after a tool call | Not trained directly |
| Trajectory | The ordered, token-faithful record of a session | One per rollout |
| Trace | A trainable segment or reconstructed sub-trajectory | Zero or more per session |
| Reward component | A normalized score for one behavior or evidence property | Many per rollout |
| Group reward | Per-rollout reward after shared and relative shaping | One per rollout |
| Advantage | Group-relative learning signal used by the optimizer | One per rollout, broadcast to its trainable tokens |

The group is the fundamental comparison unit. All rollouts in a group must use
the same prompt, tool definitions, environment configuration, and policy
version unless an experiment explicitly studies a mixed-policy setting.

## 2. End-to-end pipeline

```text
Training prompt
     |
     |  sample one prompt and create a GRPO group
     v
Grouped rollout request
     |
     |  G independent sessions for the same prompt
     v
Agentic harness
     |
     |  loop until final answer, terminal state, length limit, or timeout
     |
     |  1. build model context
     |  2. policy generates reasoning / text / tool call
     |  3. execute tool or environment action
     |  4. append observation to context
     |  5. repeat
     v
Raw rollout result
     |
     |  messages, tool calls, tool results, citations, status,
     |  token IDs, response spans, rollout log-probs, loss masks
     v
Reward pipeline
     |
     |  per-session outcome + process scores
     |  group-shared quality signals
     |  group-relative evidence and efficiency signals
     v
One scalar reward per rollout
     |
     |  gate invalid/empty sessions; keep partial usable traces
     v
GRPO advantage
     |
     |  compare each rollout against the other rollouts in its group
     v
Token-level training batch
     |
     |  train only policy-generated tokens
     |  mask observations, tool results, padding, and invalid spans
     v
Policy update
     |
     |  full model, adapter, or low-rank update
     v
Updated inference policy
     |
     |  generate the next rollout window
     v
Checkpoints, dumps, and held-out evaluation
```

## 3. What the harness must provide

The harness is the environment. It does not need to know how the policy is
trained. It only needs to execute the policy faithfully and return enough data
to reconstruct the decision sequence.

### Input contract

For each rollout, the harness receives:

- the task prompt and expected output format;
- the tool definitions and execution limits;
- a unique session identifier;
- group identity and position;
- policy version or rollout generation;
- context, output-token, and timeout limits;
- any task-specific ground truth needed by evaluators.

The harness must not silently rewrite the prompt, remove tools, replace the
model, or change tool schemas between rollout generation and training. Any such
change invalidates the recorded trajectory and the training loss.

### Output contract

A usable rollout result contains:

| Field | Why it matters |
| --- | --- |
| Final answer | Used by outcome rewards and evaluation |
| Full message history | Reconstructs multi-turn context and causality |
| Reasoning spans | Preserves model-generated hidden thought if exposed |
| Structured tool calls | Distinguishes real execution from text that merely looks like a call |
| Tool results | Provides evidence for process rewards; not directly trained |
| Citations / references | Links claims to retrieved evidence |
| Retrieved evidence IDs | Enables coverage, ranking, and credit assignment |
| Token IDs | Makes the policy loss token-faithful |
| Response spans | Identifies which tokens were policy actions |
| Loss mask | Separates trainable actions from environment observations |
| Rollout log-probs | Records the behavior policy probabilities |
| Status and finish reason | Distinguishes stop, length, tool error, timeout, and harness failure |
| Timing and token usage | Enables efficiency and bottleneck analysis |

The raw flow should be retained even when the final answer is poor. A failed
rollout can still provide a useful negative example if it contains real
trainable tokens.

## 4. Multi-turn rollout mechanics

A rollout is not one completion. It is a sequence of interactions:

```text
for turn t = 1..T:
    context_t = system + task + prior messages + tool results
    action_t  = policy(context_t)
    observation_t = harness(action_t)
```
The policy is responsible for `action_t`. The environment is responsible for
`observation_t`. Training must respect that boundary:

- tokens in `action_t` can receive policy gradients;
- tokens in `observation_t` are context only and are masked from the response
  loss;
- a tool result can influence later actions, but its literal tokens are not
  treated as model output.

This distinction is critical. If tool results are accidentally included as
trainable model tokens, the optimizer trains the policy to imitate the
environment rather than to choose better actions.

## 5. Token-faithful trajectory reconstruction

Every trainable trace should satisfy:

```text
tokens       = prompt tokens + response tokens
loss_mask    = one value per response token
rollout_lp   = one log-probability per response token
```
Rules:

1. Tokenization must use the same model, chat template, tool-call encoding, and
   special-token behavior as rollout generation.
2. `loss_mask[token] = 1` only when that token was generated by the policy.
3. `loss_mask[token] = 0` for tool results, user observations, padding, system
   inserts, compaction text not generated by the policy, and malformed spans.
4. `rollout_lp` must align exactly with the response tokens.
5. A session can expand into multiple traces, but all traces from the same
   rollout should retain the same group and session identity.
6. If a trace has no trainable token, it cannot contribute a policy gradient.
   It may still appear in dumps and reward analytics.

## 6. Reward architecture

Rewards are built in layers. The purpose is to turn a messy multi-turn session
into one stable scalar per rollout without destroying useful behavioral signal.

### 6.1 Normalize every component first

Every reward component should be mapped to `[0, 1]` before weighting.

Common mappings:

| Raw quantity | Normalization |
| --- | --- |
| Correct / incorrect | `0` or `1` |
| Fraction correct | Already `[0, 1]` |
| Judge score | Quantize or clamp to `[0, 1]` |
| Distance / cost | `1 - normalized_distance` |
| Better when lower | Min-max or soft rank inversion |
| Equal within group | `0.5`, not zero |
| Missing data | A separate missing/aborted status, not a silent zero |

Using `0.5` for equal group-relative values is important. If all rollouts have
the same efficiency, that component should be neutral. It should not falsely
make all rollouts look bad.

### 6.2 Per-session gates

The first layer asks whether a rollout contains usable behavior:

```text
gate_i = 1 if session i has a usable action sequence
       = 0 otherwise
```

A session with no generated tokens cannot be trained. A session that timed out
after producing real actions can still be useful: keep its trainable tokens,
apply its partial reward, and let the timeout or failure influence the reward.

### 6.3 Outcome rewards

Outcome rewards measure whether the final answer or task result is correct.
Typical components:

- answer correctness;
- task resolution;
- required format;
- citation correctness;
- citation recall;
- citation precision;
- claim support;
- constraint satisfaction.

For grounded question answering, citation correctness should usually be the
highest-weight outcome signal. An answer is not merely "similar to the
reference"; it should be supported by the evidence it cites.

### 6.4 Process and evidence rewards

Process rewards measure useful intermediate work:

| Signal | What it rewards |
| --- | --- |
| Evidence coverage | Fraction of required evidence found |
| Exploration distance | How quickly the rollout reached useful evidence |
| Drill-down distance | How quickly it moved from broad results to precise evidence |
| Retrieval rank | Whether useful evidence appeared near the top of results |
| Tool success | Whether calls were valid and returned usable results |
| Query diversity | Whether the rollout explored different useful queries |
| Unique contribution | Evidence found by this rollout but not by peers |
| Redundancy penalty | Repeated identical calls or repeated useless results |

Process rewards should support the desired outcome, not replace it. A rollout
that retrieves perfect evidence but gives an unsupported answer should not
receive the same reward as a rollout that uses that evidence correctly.

### 6.5 Group-shared signals

Some information is shared by every rollout in a group, for example:

- the best answer quality observed in the group;
- a group-level resolved/unresolved label;
- total evidence coverage achieved by the group;
- environment difficulty estimated from all rollouts.

Use shared signals carefully. If every rollout receives exactly the same value,
that value does **not** create within-group GRPO learning signal. It shifts the
group baseline but cancels in relative advantages.

Shared rewards are useful for:

- logging and evaluation;
- comparing different prompts;
- providing a group quality prior;
- mixing with differentiated signals.

They are not sufficient by themselves for GRPO within a group.

### 6.6 Group-relative signals

Group-relative signals compare a rollout with its peers. These create the
variance that GRPO uses.

Useful group-relative dimensions include:

```text
token efficiency       fewer tokens at equal or better quality
tool efficiency        fewer useful calls at equal or better outcome
exploration distance   reaches useful evidence earlier
drill-down distance    reaches exact evidence earlier
evidence uniqueness    contributes evidence peers did not find
answer quality rank    produces a better answer than peers
citation quality rank  produces more accurate citations than peers
```

For a lower-is-better raw cost `c_i`, a simple normalized score is:

```text
score_i = (max(c) - c_i) / (max(c) - min(c))
```

If all values are equal, use `score_i = 0.5` for every rollout.

### 6.7 Weighted final session reward

A stable reward has two properties:

1. every component is in `[0, 1]`;
2. component weights encode their intended importance.

For rollout `i` and component `k`:

```text
r_i = gate_i * sum_k(w_k * component_{i,k}) / sum_k(w_k)
```

A generic starting hierarchy for grounded tool-using agents is:

| Reward tier | Example weight share | Purpose |
| --- | ---: | --- |
| Citation and answer correctness | 50–60% | Primary objective |
| Evidence quality and use | 20–25% | Reward finding and using the right evidence |
| Answer quality | 10–20% | Judge clarity, completeness, and task fit |
| Efficiency and exploration | 5–15% | Break ties without punishing correct verbose answers |

Efficiency should be soft. A correct, well-cited answer that uses more tokens
than a peer should not receive a large penalty. A compact answer with missing
citations must not win.

## 7. Credit assignment

### 7.1 Session to trace

One session can produce multiple traces. The session reward is first aggregated
at the session level, then mapped back to every trainable trace from that
session:

```text
R(session) = reward for the complete behavior
R(trace)   = R(session)
```
Do not independently score trace fragments as though each fragment were a
separate rollout unless the experiment explicitly trains sub-decisions.

### 7.2 Session to token

The final session reward and advantage are broadcast to all trainable tokens in
that session:

```text
A_{i,t} = A_i    for every token t with loss_mask[t] = 1
```

This is a Monte Carlo policy-gradient treatment of the complete multi-turn
episode. More fine-grained value functions or per-turn credit estimators can be
added later, but the session-level reward must remain the ground truth for the
whole rollout.

### 7.3 Cross-session evidence contribution

When several rollouts explore the same task, their evidence sets can be
compared.

For session `i`:

```text
union      = union of evidence found by all sessions in the group
without_i  = union of evidence found by all sessions except i

contribution_i = coverage(union ∩ gold) - coverage(without_i ∩ gold)
```

This rewards a session that uniquely finds required evidence. A session that
only retrieves evidence already found by peers receives little differentiated
credit.

For small groups, this leave-one-out set difference is cheap and more stable
than exact Shapley calculation. Monte Carlo Shapley can be used later if
interactions between contributions become important.

### 7.4 Multi-agent or sub-agent work

If one rollout dispatches sub-agents, credit assignment must stay inside that
rollout unless the training objective explicitly rewards cooperation across
independent rollouts.

Recommended boundaries:

```text
prompt group
  └── rollout / session
        └── sub-agent or tool workflow
```

Do not copy a reward from one prompt group into another prompt group. Do not
treat sessions from different prompts as peers merely because they share a
timestamp or batch.

## 8. GRPO advantage

For a group with `G` rollouts and rewards `r_1 ... r_G`, GRPO turns absolute
rewards into relative advantages.

### Leave-one-out baseline

For rollout `i`:

```text
baseline_i = (1 / (G - 1)) * sum_{j != i} r_j

A_i = r_i - baseline_i
```

This is the preferred form when the trainer compares each sample against the
rest of its group.

### Optional standardization

Some implementations standardize within the group:

```text
A_i = (r_i - mean(r_1..r_G)) / (std(r_1..r_G) + epsilon)
```

Use standardization only when reward scale varies across tasks and the group
has meaningful variance. If every reward is identical, the group has no GRPO
gradient signal.

### Multi-trace grouping

If a session has multiple traces:

1. compute one reward for the session;
2. assign that reward to each trace;
3. average trace rewards to obtain the session reward if traces were scored
   independently;
4. assign the final session advantage to all trainable tokens from that
   session.

This prevents a session with many traces from accidentally receiving more
gradient weight than a session with one trace.

## 9. Policy-gradient objective

For a token-level policy, the basic GRPO-style objective is:

```text
J(theta) = E_groups [ (1/G) * sum_i A_i * sum_t m_{i,t} * log pi_theta(a_{i,t} | context_{i,t}) ]
```

Where:

- `A_i` is the group-relative advantage;
- `a_{i,t}` is a policy-generated token;
- `m_{i,t}` is the loss mask;
- `context_{i,t}` includes prior policy actions and environment observations;
- `theta` may represent the full model or a trainable adapter.

Practical trainers may add:

- importance ratios for off-policy or multi-epoch updates;
- ratio clipping;
- KL regularization against a reference policy;
- length normalization;
- token reweighting;
- mixed-precision and distributed data/tensor parallelism.

Those additions do not change the core rule: only policy-generated tokens are
trained, and their direction is determined by the group-relative advantage.

## 10. Asynchronous rollout and micro-batch flow

Large agentic rollouts are slow and variable. The training loop therefore
separates generation from optimization.

A typical asynchronous schedule:

```text
1. Request a window of prompt groups.
2. Generate groups concurrently in isolated harness sessions.
3. As each group finishes:
   - validate its trajectory;
   - compute rewards;
   - dump the group immediately;
   - place it in a completed queue.
4. Consume completed groups as micro-batches.
5. While the trainer updates weights, continue generating the next window.
6. After an update, synchronize the policy used by inference.
7. Drop or down-weight groups generated under an excessively stale policy.
```

Important properties:

- a completed group can be trained before the whole rollout batch finishes;
- generation can run ahead of optimization by a bounded number of groups;
- every generated group must record its policy version;
- stale groups are gated by a maximum off-policy distance;
- the trainer must not wait forever for a group that can no longer be produced.

## 11. Failure policy

| Failure | Recommended handling |
| --- | --- |
| No generated tokens | Cannot train; keep in diagnostics only |
| Empty final answer but real intermediate actions | Keep trainable actions; apply low outcome reward |
| Timeout after partial actions | Keep partial trace; reward completion/timeout signal |
| Tool error | Keep policy tokens if the model chose the call; penalize invalid or wasteful calls |
| Length termination | Keep trace; reward incomplete outcomes lower than complete correct outcomes |
| Malformed tool call | Keep generated tokens if reconstructable; penalize format |
| Missing citation | Keep answer; citation score is zero or low |
| Reward equal for entire group | No GRPO gradient; log as zero-variance group |
| Harness crash | Do not fabricate a trajectory; retry or mark unavailable |
| Reward-model failure | Do not assign zero silently; mark reward unavailable |

Only drop a session when it has no usable policy-generated tokens. Do not drop
a session merely because it timed out, returned an incorrect answer, or failed a
tool call. Those failures can be useful negative training examples.

## 12. Rollout dump contract

A dump should be written when a group is rewarded, not only when an entire
large rollout batch finishes. This makes debugging and reward auditing timely.

Minimum per-record fields:

```text
run_id
rollout_id
group_id
sample/session_id
policy_version
status
finish_reason
prompt
full message history
structured tool calls
tool results
citations
retrieved evidence IDs
token IDs
loss mask
rollout log-probs
token usage
timing
reward components
final reward
normalized advantage
judge inputs and outputs, when applicable
```

Use a unique run directory for every training attempt. Never append unrelated
runs into the same dump directory.

## 13. Monitoring metrics

Track generation, reward, and training separately.

### Generation health

- groups requested, running, completed, dropped;
- active and queued sessions;
- average and percentile rollout time;
- turns per rollout;
- tool calls per rollout;
- token usage per rollout;
- finish reasons: stop, length, tool call, timeout, error;
- empty or malformed action rate;
- inference throughput.

### Reward health

- mean, standard deviation, min, and max reward per group;
- per-scorer means;
- fraction of zero rewards;
- fraction of missing components;
- within-group reward variance;
- zero-variance group rate;
- citation recall and precision;
- evidence coverage;
- efficiency score distribution.

### Training health

- accepted versus dropped sessions;
- trainable token count;
- policy-gradient magnitude;
- KL or reference drift, if enabled;
- optimizer steps and checkpoints;
- policy staleness;
- reward trend versus rollout number;
- held-out metric trend.

## 14. Evaluation

Evaluation must use the same harness and reward pipeline as training, but must
not update policy weights.

Recommended evaluation set:

- held-out prompts never used for training;
- same tool definitions and limits;
- same context and token budgets;
- multiple samples per prompt for stability;
- separate metrics for answer quality, citation quality, evidence retrieval,
  and efficiency.

Do not declare improvement from a single training reward increase. Confirm that:

1. held-out answer quality improves;
2. citations remain correct;
3. evidence coverage improves or stays stable;
4. token and tool efficiency do not collapse;
5. reward components are not degenerate.

## 15. Reward-hacking guards

Agentic policies can exploit weak rewards. Use these guards:

1. **Citations must resolve.** A citation score requires a retrieved evidence
   object, not merely text that looks like a reference.
2. **Claim support matters.** Penalize unsupported or over-general claims.
3. **Efficiency is secondary.** Do not let brevity beat correctness.
4. **Diversity must be useful.** Reward unique required evidence, not arbitrary
   unique retrieval.
5. **Tool calls must be real.** Structured execution is required for tool-use
   credit.
6. **Repeated calls should lose value.** The same query or same result should
   not repeatedly earn discovery credit.
7. **Judges need context.** Provide question, generated answer, citations,
   source text, and reference answer when available.
8. **Missing is not zero.** Separate unavailable rewards from genuinely bad
   behavior.
9. **Shared rewards cannot fake variance.** Differentiated components must
   create within-group signal.
10. **Inspect dumps.** Component means without raw trajectories are not enough
    to debug credit assignment.

## 16. Minimal training-loop pseudocode

```text
for rollout_id in training_rollouts:
    prompt_groups = sample_prompts(batch_size)

    for prompt in prompt_groups:
        submit_group(prompt, group_size=G, policy_version=current_version)

    while completed_groups < batch_size:
        group = wait_for_next_completed_group()

        if group has no trainable tokens:
            record_drop(group, reason="zero_trainable_tokens")
            continue

        trajectories = reconstruct_token_faithful_traces(group)
        rewards = score_rollouts(group)
        advantages = grpo_leave_one_out(rewards)

        dump_group(group, trajectories, rewards, advantages)
        enqueue_training_microbatch(trajectories, advantages)

    while training_queue_has_work:
        microbatch = next_training_microbatch()
        update_policy_with_masked_token_gradients(microbatch)

    synchronize_inference_policy()
    save_checkpoint_and_metrics()
```

The generation loop and optimization loop can run concurrently, provided policy
versions and staleness are tracked.

## 17. Common symptoms and likely causes

| Symptom | Likely cause |
| --- | --- |
| All rewards are zero | Reward pipeline not receiving the raw flow; gate too strict; evaluator error |
| One turn only | Tool schema/request not reaching the model; tool-call parser mismatch; harness not continuing after tool result |
| No tool calls | Tool definitions empty; model name mismatch; parser disabled; tools stripped by proxy |
| No citations | Model never cites; citation extraction broken; citations not connected to evidence |
| Rewards exist but no update | Zero within-group variance; no trainable tokens; microbatch never reaches trainer |
| Long sequences cause crashes | Context or response budget inconsistent across generation, adapter, and trainer |
| Correct answers get low reward | Citation or evidence reward is too strict; component normalization is wrong |
| Verbose correct answers lose too often | Efficiency weight is too high |
| Poor answers get high reward | Reward hacking or unsupported citation matching |
| Trainer stalls | Rollout queue empty, data source exhausted, policy synchronization blocked, or fatal worker error |

## 18. Design principles

1. **Group identity is sacred.** Compare only rollouts from the same prompt and
   configuration.
2. **Token faithfulness is mandatory.** Do not train on reconstructed text that
   no longer matches generation.
3. **Actions and observations are different.** Train model actions, not tool
   results.
4. **Partial failure is still information.** Keep usable traces and reward
   their actual behavior.
5. **Normalize before weighting.** Every component should share a clear `[0,1]`
   scale.
6. **Differentiate where learning is needed.** Shared signals inform; relative
   signals teach.
7. **Reward the objective first.** Correct, supported answers outrank compact or
   active-looking behavior.
8. **Dump early.** Reward and trajectory diagnostics must be available while a
   run is still live.
9. **Version every rollout.** Off-policy data must be identifiable.
10. **Evaluate without updating.** Training reward is not proof of general
    improvement.

## 19. Glossary

| Term | Definition |
| --- | --- |
| Action | A token sequence generated by the policy |
| Advantage | How much better or worse a rollout is than its group baseline |
| GRPO | Group-relative policy optimization that compares sampled rollouts for the same prompt |
| Group | The set of peer rollouts generated for one prompt |
| Harness | The environment that executes prompts, tools, and sessions |
| Loss mask | Per-token indicator deciding whether a response token receives policy gradient |
| Rollout | One complete sampled attempt in the environment |
| Session | The stateful execution container for one rollout |
| Trace | A token-faithful trainable representation of all or part of a session |
| Trajectory | The ordered sequence of actions and observations in a rollout |
